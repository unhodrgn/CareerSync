## 1. Overview

**CareerSync** — 기업 맞춤형 AI 채용 매칭 플랫폼 (criteria-based hiring and job matching).

**Idea.** Each company defines **evaluation criteria + weights** per job. The same criteria are used to (1) score applicants and (2) recommend the company's jobs to people who have not applied. AI provides scores and evidence only; **the recruiter makes every decision**.

**Users.** `company` (recruiter; 1 account = 1 company) and `seeker` (job seeker).

**End-to-end flow**

```
Company: register → profile → create job (draft) → (optional) AI suggests criteria → save criteria (guardrail) → publish
Seeker:  register → upload CV PDF → AI structures it → edit + confirm → browse jobs → apply
System:  create evaluation (pending) → background task scores each criterion → store scores + evidence
Company: applicants ranked by Fit → per-criterion score + evidence → change status
```

## 2. Architecture

| Part        | Technology                                                                                                                                | Location                                  |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| Frontend    | React 19, TypeScript, Vite, React Router. Korean UI, desktop-first                                                                        | `frontend/`                               |
| Backend     | Python 3.11+, FastAPI, SQLAlchemy 2, Alembic, Pydantic 2                                                                                  | `backend/app/`                            |
| Database    | PostgreSQL 16 (tests: in-memory SQLite, or a disposable local PostgreSQL via `TEST_DATABASE_URL`)                                                            | `backend/migrations/`                     |
| AI          | Groq (`openai/gpt-oss-120b`, demo default) or Anthropic Claude via `LLMClient` (`LLM_PROVIDER`, D91), sentence-transformers `intfloat/multilingual-e5-base` (fallback `hashing-ngram-v1`), PyMuPDF, Tesseract (local poster OCR) | `ai/`                                     |
| Auth        | JWT HS256 (PyJWT), Argon2id passwords, Bearer token                                                                                       | `backend/app/core/security.py`, `deps.py` |
| Static data | Legal blocklist, skill dictionary (YAML)                                                                                                  | `data/`                                   |
| Infra       | Docker Compose: `db`, `init` (migrate + seed), `backend`, `frontend`, and the optional `agent` (profile `voice`)                          | `docker-compose.yml`                      |

```mermaid
flowchart LR
    B[Browser] -->|:3000| FE[Vite / React]
    FE -->|/api proxy| API[FastAPI :8000 · api/v1]
    API --> SVC[services]
    SVC --> DB[(PostgreSQL)]
    SVC --> RT[ai_runtime]
    RT --> AI[ai/ · parsing · scoring · guardrails · embedding]
    AI -->|only with AI_MODE=llm| LLM[LLM API: Groq / Anthropic]
    AI --> DATA[data/*.yaml]
    SVC -. BackgroundTasks .-> EV[evaluation_service.run_in_background]
```

**Layers.** `api/v1` checks permissions (dependencies `CurrentUser`, `CompanyUser`) and maps schemas → `services` hold business logic and DB access, and call `ai/` through `services/ai_runtime.py` → `models` are the ORM. `ai/` never imports `app.*`.

**Errors.** Services raise `AppError(status, CODE, "Korean message", **extra)` → JSON `{"code", "message", ...}`. Validation errors: 422 `{"detail": [...]}`. Missing/invalid token: 401; non-company on a company route: 403. Another company's job returns 404 `JOB_NOT_FOUND` on purpose.

**Main data flows**

- **CV upload:** PDF (≤ 5 MB, ≤ 5 pages, text only) → `ai.parsing.pdf` → `ai.parsing.pii` masks PII → `cv_documents.masked_text` (the PDF itself is not stored) → `structure_cv` (LLM or rules) → `CvProfile` → `cv_service._fill_relational_profile` writes it into the `cv_*` tables as profile version 1.
- **CV read:** `cv_service.to_profile_data(row)` rebuilds the `CvProfile` model from the `cv_*` tables. The API response and the AI input both use this `CvProfile` shape (`cv_profile.v1`).
- **CV edit:** every save creates a new `cv_profiles` version (new child rows); `confirm=true` sets `confirmed_at`.
- **Apply:** seeker + published, unexpired job + AI consent + newest CV confirmed + not applied → `applications` + `evaluations` (pending, keyed by job × CV version) → background scoring → `criterion_scores`.
- **Ranking:** Fit is computed at read time from stored scores and the **current** weights (`criteria_service.load_for_scoring`), so a weight change re-ranks without any AI call.

### 2.1 Practice interview architecture [Planned]

The seeker practice interview is decided (D51–D62). The pure engine `ai/interview/` exists, with its model-independent LLM layer and the final feedback generator ([§6.2](#62-practice-interview-engine)). Of M4 (backend and database), the tables, the daily quota ledger, the backend services (stages S1 to S3c: lifecycle, ingestion of turns and of the end, the feedback service) and the seeker API (the seven endpoints of D67, stages S4.1 to S4.5) exist (§3.7); of M5 (D80, D81), the internal agent API (stage S1), the agent core with a text driver for developers (`interview_agent/`, stage S2), the consent-withdrawal rule (S3), and the voice worker with optional Anam Avatar integration (`D90`, falling back gracefully to audio-only), the seeker's join token, and a developer test page (`interview_agent/devclient/`) exist. On 22/11/2026 and 23/11/2026, live voice runs (`AI_MODE=llm`, sessions 3 and 6) verified room dispatch, Korean turn detection, end-to-end latency, the Groq timeout fallback, live PII masking, and a join into an existing room; on 25/11/2026, the Compose `agent` image switched to the frozen Linux lock (`interview_agent/requirements.linux.lock.txt` with `--no-deps` and `pip check`), and sessions 8 to 11 on the Compose stack (driven by a headless `livekit.rtc` participant interrupting active agent TTS audio) closed the remaining live checklist items (`C6a` timing, `C6b`–`C6d`, `C8`, Compose `rules` mode, live backend `GroqClient` plan generation, and PostgreSQL feedback). Anam Avatar with audio-only fallback (`D90`) is wired and live-verified on Compose across sessions 12 to 14 (`interview_agent/` `voice.py`, `config.py`, `timing.py` and `interview_agent/devclient/`: audio-only mode, error fallback, and live Anam video/audio streaming); still planned: M6 (full frontend rebuild including interview UI, D88).

```mermaid
flowchart LR
    SK[Seeker browser] -->|JWT| API[FastAPI]
    API -->|session and microphone-only LiveKit token| SK
    SK -->|audio| LK[LiveKit room]
    LK --> AG[Interview Agent: own runtime]
    AG -->|service secret, internal API| API
    AG --> ENG[ai/interview engine]
    AG -->|masked text, per-turn analysis| GROQ[Groq]
    API --> ENG
    API -->|plan and feedback| LLM[ai_runtime.llm: Groq / Anthropic]
    API --> DB[(PostgreSQL)]
```

| Step                            | Where                                | Model (D52)                                                                                                       |
| ------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| Plan (questions, rubric points) | Backend, when a session is created   | `ai_runtime.llm()` in `AI_MODE=llm`, else the template; the D21 question bank is reused and cached                |
| Per-turn answer analysis        | Interview Agent                      | Groq `openai/gpt-oss-120b` through LiveKit's Groq plugin, or the engine's rules (D54); `AI_MODE=rules` uses rules |
| Final feedback                  | Backend, when the seeker asks for it | `ai_runtime.llm()` in `AI_MODE=llm`, else the rules version                                                       |

- **The engine decides, everything else carries.** The agent is a separate runtime (`interview_agent/`, D56). It hands each transcribed answer to the engine and speaks the engine's next line; it never decides what to ask and never touches the database. The backend builds the plan, checks the D51 gates, stores the masked turns and writes the feedback.
- **Tokens and internal calls (D58).** The browser gets a microphone-only LiveKit token for one new room (no camera or screen track). The agent is dispatched with only the session id as metadata, because a participant can read the metadata inside its own token. The internal endpoints accept a service secret that the browser never sees and the room name of the session, and only while the session is created or live. That check lives in its own module; `backend/app/core/security.py` and `backend/app/core/deps.py` stay unchanged.
- **Privacy (D53).** Masked text only, never audio or video. Spoken text is masked before any model sees it, then masked again and its quotes re-verified by the backend before storing. Only the owning seeker reads a transcript or its feedback; companies never do. Sessions can be deleted and expire after 30 days. Consent and expiry are decided in D65 (a consent per session, a 30-day expiry that hides the session, and a deletion that a lazy purge and a script carry out, the script needing an external scheduler); the processors involved are Q35, still open.
- **Modes (D54, D55).** `AI_MODE=rules` needs no key: the engine's rules, template questions, rules feedback. A failing model call degrades that one turn to the rules and records the method. Interviews work audio-only; the avatar is optional.
- **Unchanged by this feature:** `ai/llm/client.py`, scoring and the company side. The interview reads no evaluation and no weight.

## 3. Database

PostgreSQL 16, Alembic migrations `0001` → `0012`. List the current tables with:
`python -c "import app.models; from app.db.session import Base; print(sorted(Base.metadata.tables))"` (from `backend/`).
JSON columns are `JSONB` on PostgreSQL and `JSON` on SQLite. All `created_at`/`updated_at` columns are `timestamptz` with `now()` defaults.

### 3.1 Accounts and companies

**`companies`** — `id` PK · `name` varchar(100) · `intro` text (≤1000) · `talent_profile` text (인재상, ≤1000; added to scoring of `other` criteria) · `created_at`, `updated_at`

**`users`** — `id` PK · `email` varchar(255), unique on `lower(email)` · `password_hash` (Argon2id) · `display_name` varchar(50) (shown to recruiters, masked out of CV text) · `role` `seeker`|`company` · `company_id` FK → companies (CASCADE; required when role is company) · `consent_privacy_at`, `consent_ai_at` (AI consent required to apply), `consent_version` · `created_at`

### 3.2 Jobs and criteria

**`job_postings`** — `id` PK · `company_id` FK → companies (CASCADE) · `title` varchar(200) · `description` text (JD, ≤10000, required to publish) · `employment_type` `full_time`|`contract`|`intern` · `min_experience_years` smallint 0–30, NULL = 신입 가능 (entry level allowed) · `location`, `salary_note` varchar(100) free text · `deadline` date · `status` `draft`|`published`|`closed` · `criteria_updated_at` · `published_at`, `closed_at` · `created_at`, `updated_at`.
After publishing only `deadline`, `location`, `salary_note` change; `closed` is final; only drafts can be deleted.

**`job_criteria`** — `id` PK · `job_id` FK → job_postings (CASCADE) · `name` varchar(50), unique per job on `lower(trim(name))` · `description` text (rubric, ≤500) · `category` `skill`|`experience`|`project`|`certificate`|`education`|`other` · `weight` 1–100 · `position` · `guardrail_version` · `created_at`, `updated_at`.
Service rules: 1–`CRITERIA_MAX_ITEMS` criteria, unique names, weights sum to `CRITERIA_WEIGHT_TOTAL`; an `education` criterion names at least one major or 이공계/STEM (checked on draft save, copy and publish); after publishing only weights and order change.

**`criteria_guardrail_logs`** — one row per blocked input: `company_id` FK (CASCADE), `job_id` FK (SET NULL), `input_name`, `input_description`, `rule_id`, `category`, `law_ref`, `blocklist_version`, `created_at`.

### 3.3 CVs

**`cv_documents`** — `id` PK · `seeker_id` FK → users (CASCADE) · `file_name` · `sha256` (unused so far) · `pages` · `masked_text` (the only text the LLM and evidence checks see) · `masked_kinds` JSON · `created_at`

**`cv_profiles`** — one row per CV version: `id` PK · `cv_document_id` FK (CASCADE) · `seeker_id` FK → users (CASCADE) · `version` (unique per document) · `schema_version` (`cv_profile.v1`) · `method` (`rules`, `llm:<model>`, `seeker`) · `summary` text · `confirmed_at` (only confirmed versions can be used to apply) · `created_at`.

Child tables of `cv_profiles` (all `cv_profile_id` FK → cv_profiles, CASCADE, indexed; read back in `id` order):

| Table              | Columns                                                                                                                 |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `cv_skills`        | `skill_name` varchar(100)                                                                                               |
| `cv_experiences`   | `org`, `role` varchar(100) · `start`, `end` varchar(7) `YYYY-MM`, nullable · `description` text · `source` varchar(500) |
| `cv_projects`      | `name` varchar(200) · `role` varchar(100) · `description` text · `source` varchar(500)                                  |
| `cv_project_techs` | `cv_project_id` FK → cv_projects (CASCADE) · `tech_name` varchar(100)                                                   |
| `cv_educations`    | `school`, `major` varchar(100) · `degree` varchar(20) · `source` varchar(500)                                           |
| `cv_certificates`  | `name` varchar(100) · `date` varchar(7) nullable · `source` varchar(500)                                                |

`source` = the CV line an item was read from. Seekers can edit it (see [issue 3](#11-known-issues-and-risks)).

### 3.4 Applications and evaluation

**`applications`** — `id` PK · `job_id` FK (CASCADE) · `seeker_id` FK → users (CASCADE) · `cv_profile_id` FK → cv_profiles (**RESTRICT**) · `status` `submitted`|`reviewing`|`interview`|`on_hold`|`passed`|`rejected` (recruiter only) · `status_updated_at` · `created_at`. Unique (`job_id`, `seeker_id`).

**`evaluations`** — `id` PK · `job_id` FK (CASCADE) · `cv_profile_id` FK (CASCADE) · `status` `pending`|`done`|`failed` · `error` · `llm_model`, `embedding_model`, `prompt_version`, `skills_version` · `created_at`, `finished_at` · `queued_at` timestamptz, nullable · `attempts` smallint ≥ 0, default 0. Unique (`job_id`, `cv_profile_id`) — keyed by job × CV version, **not** by application, so recommendation can reuse it.

`queued_at`/`attempts`: migration `0008` (backfill `queued_at = created_at`, `attempts = 1`). Set by `evaluation_service.claim()` on every queue (apply, retry); the run writes its result only while `queued_at` still equals the value it was queued with (fencing). Rules: [§6.1](#61-recommendation).

**`criterion_scores`** — `evaluation_id` FK (CASCADE) · `job_criteria_id` FK (CASCADE) · `score` 0–100 · `level` · `reason` · `evidence` JSON (quotes) · `method` (`rule:skill`, `llm:<model>`, `retrieval`, …). Unique (`evaluation_id`, `job_criteria_id`). Weights are **not** stored.

### 3.7 Planned: practice interview tables [Planned]

The tables and the daily quota ledger `interview_quota` exist since migration `0012`. Stage S2 added the backend services that create, read, end and delete sessions and purge expired ones; until S4 no endpoint exposed them, and since S4.1 one router, `backend/app/api/v1/interview_sessions.py`, serves the seeker API (S4.1 to S4.5: the consent text, the creation, the history, the detail, the end, the delete and the feedback of a session). Stage S3a added the services that store the turns and the end of an interview (`record_turn`, `record_end`); nothing calls them yet, since the agent that would is M5. Stage S3b added the feedback service (`stored`, `ensure`); the feedback route (S4.5) calls `ensure`, and `stored` has no caller. The tables below are the schema of migration `0012`, as the models in `backend/app/models/interview.py` define it. They replace the earlier working design: there is no `expired` status (expiry is derived from `expires_at`), and no room-name or avatar column. Where a column holds JSON it is `JSONB` on PostgreSQL, and a null is stored as SQL NULL.

**Implemented in M4 S1–S3c (services) and S4.1–S4.5 (the seven seeker endpoints, the no-store mechanism, the validation-error sanitizer and the route class that completes the `Allow` header).**

- **Quota ledger** (`interview_quota_service`). Three independent daily limits per seeker and KST day: session reservations, planning-model attempts and feedback-model attempts (3 each). One conditional `UPDATE` takes a reservation, and a database CHECK keeps `used` within the limit the row was created with. A reservation is committed before the work it pays for, and it is never refunded: not when the model fails, not after a crash or a refused plan, not when the session is deleted (the table has no link to a session). The claim has not yet been run against PostgreSQL concurrency tests (they are written and skipped without a PostgreSQL URL).
- **Consent** (`interview_consent_service`, D65). A per-session transcript consent: an explicit `true` and the exact `INTERVIEW_CONSENT_VERSION`, checked after the global AI consent, the confirmed CV and an open job, and before the criteria, the CV text or a model are touched. The wording is an implementation draft, not a legal approval, and it does not name the processors (Q35).
- **Plan** (`interview_plan_service`). The stored masked CV goes only to `clean_cv` and to `build_plan` (which needs it to keep the lines `clean_cv` removed, D62); the planning model gets the cleaned text only, through `make_bank`, `GatedClient`, `compose` and `ask`. Bank questions that repeat a CV line word for word (12 characters or more) or a removed line are dropped, every CV quote is cleared, and there is no CV-grounded warm-up. The plan is validated again without the CV, must be a fixed point with no issue, and passes a last scan before its canonical JSON and SHA-256 are stored. Never stored: the raw or cleaned CV, an excerpt, a CV quote, the question bank, a weight. **Limit:** the plan can still hold professional questions that the model or a template wrote from the cleaned CV, in other words. The word-for-word check does not see a paraphrase, and `clean_cv` is a vocabulary cut (Q24 is unresolved), so the plan is not guaranteed to be free of CV-derived information. Everything stored is readable by its owner only and expires with the session.
- **Lifecycle** (`interview_service`). Create takes its session and quota reservations in one short transaction (T1) with a 120-second planning lease, reads the CV and calls the model with no transaction open, and stores the plan with one compare-and-set (T3) that does not bring back a deleted, expired or superseded reservation. A seeker has at most one planning, created or live session. A session can be joined for 300 seconds after its plan is ready and runs for 600 seconds; after that only the final end event and the closing agent line are to be accepted, for 30 more seconds, and never a candidate answer (`record_turn` and `record_end` below enforce this by the backend clock at receipt). A session past its deadline is `aborted` for every reader (`not_joined`, `planning_lost` or `stale_live`): detail and history show this status without changing the row, while create, end and `scripts/purge_interviews.py` settle the row to the same status without touching the quota. End is idempotent; Delete is final, and a repeated Delete returns 404. Both are owner-only; another seeker's session or an expired one is a 404, and a company user gets a 403. History also returns `active` (`HistoryPage.active`, D67): the seeker's one planning, created or live session as `interview_time.derive` reads it at the same clock value as the items, or none. It is looked up on its own, so it does not depend on `job_id`, `limit` or `before_id`, and it is a read like the rest of the history: a session past its deadline reads `aborted` and is not active, and no row is settled.
- **Retention (D65).** `expires_at` is created_at + 30 days and never extended, and an expired session is hidden from every read. The app deletes the seeker's own expired sessions on create, history and delete, and at most 50 of anyone's on create. `scripts/purge_interviews.py [--dry-run] [--batch N]` settles stale sessions, deletes all expired ones with their turns and the quota rows of days before today, and prints counts only. **Nothing in the app or Compose runs it on a schedule**: a deployment must configure one (cron, a task scheduler, or `docker compose run --rm backend python scripts/purge_interviews.py`). Until it does, expired data is hidden, but not all of it is deleted.
- **Ingestion** (`interview_ingest_service`, S3a). `record_turn(db, session_id, event)` and `record_end(db, session_id, event)` take a session id and no user: the endpoint that will call them (M5) must authenticate the agent and bind it to the session. They validate and store what the Interview Agent says and hears, and they trust the agent for the coverage (the status of each topic and the rubric levels) and for the words. They check the shape, the relation to the stored canonical plan (its digest, and the topic echoed for each item index), the engine's rules and the clock; they never work out, improve or infer a status or a skill from a text or from an analysis. A buggy or compromised agent can still forge statuses and lines. **Turn:** strict types; role and kind pairs (`closing` only inside the end event); an item index into the plan; the text masked again, agent lines too, at most 4000 masked characters and 8000 raw, refused and never cut (an empty candidate answer is valid); a candidate's quotes verified again against the masked answer (an unverifiable one is dropped); the analysis checked and stored, never used for the coverage. **Sequence:** `seq == last + 1`, otherwise 409 `INTERVIEW_SEQ_GAP` with `expected_seq`; regular turns take 1 to 119 and the closing line may take 120. The same sequence number with the same identity (role, kind, item index, masked text) is a duplicate: nothing is written and the coverage is untouched; with another identity it is 409 `INTERVIEW_SEQ_CONFLICT` and the first write stays. The plan and the topic echo are checked before a duplicate is acknowledged. **Time:** by the backend clock at receipt. The first turn of a `created` session (seq 1, the engine's first question) starts it, and `active_until` becomes the start plus 600 seconds. A turn on the deadline is accepted and a turn after it is refused, candidate or agent. For the next 30 seconds only an end event is accepted. A turn that finishes after the 600 seconds is therefore dropped, and the stored transcript can lack the last answer the engine heard. **Coverage:** the snapshot of `coverage_snapshot(state)` after the turn, with exactly its four keys, phase `listening` and no end reason on a turn event (the agent must set both, even when its call ended the interview: the end event carries the final phase and reason), the topics of the stored plan, the engine's status and level vocabularies, the points of each topic's rubric, at most 4096 bytes. Against the stored coverage: a status may only make the transitions the real engine makes (a test drives the real engine and fails if it produces another one, or if an allowed one is never produced), a rubric level never goes down or disappears, and a status or levels that only an answer can give need a stored candidate answer for that topic. **End:** one final snapshot (phase `ended` or `aborted`) and, only for `ended`, the closing line. Accepted until the deadline plus the 30-second grace, for a live session. The status (`completed` or `aborted`), the final coverage and the closing line are one transaction. The end reason is one of `plan_exhausted`, `empty_plan`, `time`, `candidate_left`, `session_closed`, `agent_error`, `agent_ended`; the part of a value before a colon counts, and anything else is stored as `agent_ended` (a free-form reason is never stored). An end retried with the same payload (status, reason, final snapshot and closing line) is a duplicate; any other payload for a session that is over is 409 `INTERVIEW_ALREADY_ENDED`, including a different closing line. **Concurrency:** each write starts with one guard `UPDATE` that checks the status and the deadline and takes the row lock (PostgreSQL), and the checks that need the stored state are read under it, so a turn, an end, the seeker's End and the settlement cannot all win; `UNIQUE (session_id, seq)` is the backstop. No model is called, so the lock lasts a few statements. The behaviour under real parallel requests is covered by PostgreSQL-only tests that have not been run; SQLite tests of the same races step through them on one connection and prove nothing about PostgreSQL. **What the agent (M5) must do:** post events one at a time in order and resend a refused gap; stop and abort the session after a permanent refusal (a 422, or a conflict), because a refused event leaves a sequence gap that would break every later one; set phase `listening` on turn events; post a candidate's answer before the 600-second deadline.
- **Feedback** (`interview_feedback_service`, S3b, D64). `stored(db, user, session_id)` returns the stored report or `None` and never generates; `ensure(db, user, session_id)` returns it or makes it once, as a `FeedbackResult` (`data`, `final`, `limited`, `reason`, `method`, `prompt_version`, `generated_at`, `attempts_used`). The service adds no `AI_NOTICE`: the response schema `FeedbackOut` (S4.5) does. **Who and when:** seekers only, and only the owner (another seeker's, an expired and a deleted session are one 404, a company user gets 403). A stored report is returned first and stays readable after the AI consent is withdrawn; every new generation, rules and provisional reports included, needs the current AI consent (409 `AI_CONSENT_REQUIRED`) but not a confirmed newest CV. The interview must be over, `completed` or derived `aborted` (a stale `live` session counts; otherwise 409 `INTERVIEW_NOT_ENDED`); an aborted session whose last coverage still says `listening` gets the engine's interruption note, with no topic status changed. **Input:** the two safe views only (`plan_view_from`, `transcript_view_from`, then `make_feedback`); no CV text, raw state, raw turn or raw serialization. A turn's topic comes from the original order of the digest-checked stored plan, not from the validated plan, which can drop items; a plan with no faithful mapping is 409 `INTERVIEW_PLAN_INVALID`, and a plan whose digest does not match, or that validation still changes, gets a provisional rules report (`plan_invalid`) with no model, no quota and no attempt. **Fallbacks:** rules mode or no candidate answers: the rules report is stored as final (no quota). Quota used up: provisional rules report, `limited=true`, nothing kept. A model failure on attempt 1 or 2: provisional rules report (`model_failed`), not stored, lease freed; on attempt 3: the rules report is stored as final. A usable report: stored with `llm:<model>` and the prompt version. A valid lease held by another request: 409 `INTERVIEW_FEEDBACK_BUSY` with `retry_after_seconds`. **Lease, attempts, quota:** 120 seconds, 3 attempts per session and 3 reservations per seeker per KST day (the constants table in §9); a 120-second lease outlasts a normal call (about 90 s at most, `ai/llm/client.py`). T1 (one transaction) takes the lease, the attempt and the reservation together, and a refused reservation rolls all three back; the model is called with no transaction and no row lock; T3 stores only for the token that holds the lease and only while there is no report; a release is fenced by the same token. A stale worker therefore never clears or overwrites a newer worker's lease or result: it returns the stored report if there is one, else its own report provisionally (`lease_lost`), and 404 when the session is gone. The fence is the token, not the clock. Attempts and reservations are never refunded. A session whose third attempt never finished gets the rules report stored by the next request, with no model call. **Limits:** a stored report is not screened again when read; leases use the application clock; the SQLite tests of the races prove the logic only, and the PostgreSQL concurrency tests (`backend/tests/test_interview_feedback_concurrency.py`) are written and have not been run against PostgreSQL; Q24 and Q35 are unresolved.
- **Hardening** (S3c and S3c.1, D65, D66, D92). *Retention tests* no longer depend on the date: `scripts/purge_interviews.py` takes an injectable clock through its `main` function (a test seam and not an option: the command line is unchanged and uses the real clock), the tests derive their days from a clock they set and run it at four instants, among them the first and the last second of a KST day, and a tripwire fails any read of the wall clock by the time and quota services. *U+0000* is refused and never stripped, because PostgreSQL `TEXT` and `JSONB` cannot store it and SQLite can. A turn that has one, a closing line too, is 422 `INTERVIEW_BAD_TURN` with `field` `text`, before anything is written. A plan is refused (`PlanRefused`, so 422 `INTERVIEW_NOT_AVAILABLE`) when the cleaned CV has one (before any model sees it), when the questions the model made have one, or when the canonical plan has one anywhere, keys included. A feedback that a model wrote and that has one anywhere (a sentence, a quote, the model's name) is rejected as a whole before it is persisted, never cleaned, and handled through the existing failed-model-call path: the rules report, provisional on attempts 1 and 2 (`model_failed`) and stored as final as of the last attempt, with the attempt and the reservation spent as for any failed call; no part of the rejected report is stored, and there is no new error code (S3c.1, D66). *SQL parameters:* the engine is built with `hide_parameters=True` (`ENGINE_OPTIONS` in `backend/app/db/session.py`), so a database error or an SQL log line no longer carries bound values (masked transcripts, plans, feedback, CV text). It does not hide what PostgreSQL itself writes into the detail of an error (a check or not-null violation names the failing row), which is why values are validated before they are stored. *D21 & LLM failure logs:* `make_questions` and the other LLM callers (`ai/parsing/extract.py`, `ai/scoring/scorers.py`, `ai/career/cv_review.py`, `ai/career/roadmap.py`, `ai/career/verification.py`) log only the exception type (`type(e).__name__`) or a generic failure warning on `LLMError`, never raw exception text or model responses (D65, D92). A question that a blocklist drops, from the template or from the model, is logged at INFO by reason, source (`template` or `llm`) and criterion id (an id that is one of the job's criteria, otherwise none), and never by its text (S3c.1, D66). *PostgreSQL tests:* the `db` fixture drops every application table, so a PostgreSQL `TEST_DATABASE_URL` is accepted only for a disposable local database (PostgreSQL, one loopback host, a name ending in `_pgtest`, no query parameter that can name another server) and is refused before any connection, without printing the URL or the credentials (`backend/tests/db_safety.py`); SQLite is unchanged. `test_interview_create_concurrency.py` (simultaneous creates of one seeker: one winner, the quota taken once, the losers rolled back) and `test_interview_nul_postgres.py` are written and have been verified on PostgreSQL (D77). **Limits:** the `params` attribute of a SQLAlchemy error still holds the values in memory, though nothing logs it; Q24 and Q35 remain unresolved.
- **Processor caveat (Q35, open).** In model mode (`AI_MODE=llm` with a key) the model call of feedback sends PII-masked transcript text of the two safe views (never the CV, the PDF, the display name or an email) to the configured processor behind `ai/llm/client.py` (`GroqClient` when `LLM_PROVIDER=groq`, `AnthropicClient` when `anthropic`). The transcript consent text (D65) does not name any processor, and Q35 remains unresolved (widened in D91). This paragraph describes the caveat; it is not legal approval.
- **Other M5 constraints.** The agent must send only `ModelInput.system` and `ModelInput.user` to its model (D62), must treat a 409 `INTERVIEW_ALREADY_ENDED` after the seeker ended the session as final, and a 404 `INTERVIEW_NOT_FOUND` after the seeker deleted it as a reason to stop and disconnect (the delete route does not notify a live agent), and audio-only / Anam fallback behavior applies per D55 and D90. The agent's endpoints authenticate the agent and bind it to one session. LiveKit dependencies belong to `interview_agent/` and planned M6 frontend (D56).
- **Operational requirement.** Physical deletion of expired sessions needs a scheduler that a deployment configures and runs outside the app (D65); until then expired data is only hidden. The PostgreSQL tests of the interview (quota, ingestion, feedback, create, NUL) need a disposable local database as described for `TEST_DATABASE_URL` in §9.
- **API** (S4, D67 and D69; stages S4.1 to S4.5). The seeker API is built stage by stage. A route is registered only in the stage where its service integration is implemented: no placeholder and no 501 route exists, and a contract test fails when the registered interview routes differ from the stage's list. **S4.1** registers `GET /api/interview-consent` (any logged-in user, company included: the static text and version of `interview_consent_service.current()`, no personal data, no notice, no database write, no quota, no model call) and the mechanism that puts `Cache-Control: no-store` on every response under the interview paths (`/api/interview-consent`, `/api/interview-sessions…` and `/api/jobs/{id}/interview-sessions…`, not the D21 `/interview-questions` route): `backend/app/core/no_store.py`, a pure ASGI middleware and a handler for unexpected errors, installed last in `main.py`. The middleware covers every response made inside the application: success, 401 and 403, `AppError`, 422, 404, 405, the trailing-slash redirect and the 429. The handler is needed because Starlette makes the 500 response outside every user middleware. It delegates to the generic handler the framework would have used (none exists today, so Starlette's default text `Internal Server Error`), runs a synchronous handler in the thread pool and not on the event loop, and changes nothing outside the interview paths; the server still logs the error. Tests cover each kind of response on throwaway applications and on the real route, compare the response outside the interview paths with an application that has no `install`, and walk the real stack (in front of the middleware there are `ServerErrorMiddleware`, a telemetry layer that makes no response and, from FastAPI 0.164, `AppBodyLimitMiddleware`, which FastAPI adds on its own and which is a pass-through while no request body limit is set; the test accepts the stack with or without that last layer and fails on any other layer or order, so a library upgrade that adds a layer fails a test; it also fails if a body limit is set on the application, a router or a route, because a limit on the application would give a 413 outside the middleware without the header, D78). **S4.2** registers `POST /api/jobs/{job_id}/interview-sessions` and adds nothing to what `interview_service.create_session` does: seeker-only, the AI and the transcript consent, the confirmed CV, the open job, the quota and the one-active-session rule are the service's, and the route returns its result with status 201. The clock reaches the service through the overridable dependency `get_clock` (the real clock by default), so no API test depends on the real date. The two consent fields are untyped, so nothing is coerced (`"true"` is not `true`). A validation error on an interview path (422) is cut down to `type`, `loc` and `msg` (D68). FastAPI's default response also carries `input` (the submitted value, and the whole body when it is not an object) and `ctx` (the validation context), and for an unknown field its client-supplied name as the last element of `loc`. `backend/app/core/validation_errors.py` removes `input`, `ctx` and, for an `extra_forbidden` error, that last element of `loc`, and keeps the rest of `loc`. It applies to the interview API paths only, matched by the same `is_interview_path` test as the no-store middleware. Validation messages on those paths must be fixed sentences that never interpolate a submitted value, and a validator that builds its message dynamically must be reviewed before it is added. Every other path keeps the handler it had: the sanitizer captures the previously registered handler and delegates to it. The no-store header of D67 still covers the sanitized 422. The request body is not logged by anything of this stage. The request URL (an id) is still in the server's access log, as for every route. **S4.3** registers `GET /api/interview-sessions`, the seeker's history, and changes the service in one way: `interview_service.HistoryPage` gains `active`, the one added field of D67 (3); the items, the cursor, the page size, the retention purge and the lifecycle are as before. The route has the optional integer parameters `job_id`, `limit` and `before_id`. `job_id` and `before_id` accept the signed 32-bit range of the id columns (`Integer`), -2147483648 to 2147483647, and a value outside it is a 422 in the D68 shape, as is a value that is not an integer; the `msg` of a bound error holds the fixed bound and never the submitted value. `limit` has no bound: the service clamps it. It answers 200 for any seeker (inside that range an unknown job or a non-positive id is an empty page and not a 404; a company user gets 403 `SEEKER_ONLY`), and it has no quota, no model call and no consent gate, so it works after the AI consent is withdrawn (D67 (8)). `active` is always in the response and is `null` when there is none. It is the same summary as an item and is looked up on its own, so it does not depend on `job_id`, `limit` or `before_id`, and it is in `items` as well when it is on the page. It is read-only: a session past its deadline reads `aborted` and is not active, and a GET settles nothing. Its tests are `backend/tests/test_interview_api_history.py` (HTTP, OpenAPI and no-store), `backend/tests/test_interview_history_active.py` (service), and the stage lists of `backend/tests/test_interview_api_contract.py` and `backend/tests/test_interview_api.py`. **S4.4** registers the three routes of one session: `GET /api/interview-sessions/{session_id}` (the detail), `POST /api/interview-sessions/{session_id}/end` and `DELETE /api/interview-sessions/{session_id}`. The path id has the same signed 32-bit range as `job_id` and `before_id` (-2147483648 to 2147483647): a value outside it, or one that is not an integer, is a 422 in the D68 shape with `loc` `["path", "session_id"]`, before any service is called. The detail answers 200 with the `SessionOut` of the create response (D67 (7)). It is seeker-only, and a missing, expired, deleted or another seeker's session is the same 404 `INTERVIEW_NOT_FOUND`. It is a read: no status is settled, no expired session is purged, and there is no quota, no model call and no consent gate, so it works after the AI consent is withdrawn (D67 (8)). The status is derived from the deadlines, so a session past its deadline reads `aborted` with its reason, and nothing internal leaves the response: no plan, coverage, feedback body, CV text, rubric or weight. **The end** (`POST /api/interview-sessions/{session_id}/end`, with no body: a body that is sent is ignored) answers 200 with the same `SessionOut`, the session as it is after the call, and its rules are the service's, not the router's. The service first settles the seeker's own stale sessions, which can be another session than the one asked for and is done before a 404 too, and then looks the session up (404 `INTERVIEW_NOT_FOUND`, as for the detail). A session still being planned with a valid lease is a 409 `INTERVIEW_PLANNING` (`code` and `message` only, nothing changes), and one whose lease has run out reads, and is settled, as `aborted` with `planning_lost`. A `created` session up to its join deadline, and a `live` one up to its deadline plus the end grace (`INTERVIEW_END_GRACE_SECONDS`), becomes `aborted` with the reason `seeker_ended`, `ended_at` the time of the request and `active_until` null, by one compare-and-set update; a session past that keeps the reason it was settled with (`not_joined`, `stale_live`), and a completed or an already aborted one is returned as it is, so a repeated End gives the same 200 and the same `ended_at`. **The seeker's End inserts no closing line and no agent end event, and it does not call `interview_ingest_service.record_end`: the agent's final event and closing line are M5.** It changes no quota, makes no model call, does not purge, and works after the AI consent is withdrawn. **The delete** (`DELETE /api/interview-sessions/{session_id}`, with no body: a body that is sent is ignored) answers 204 with an empty body, and its rules are the service's. The service first deletes the seeker's own expired sessions (before a 404 too, and never another seeker's), then looks the session up (404 `INTERVIEW_NOT_FOUND`, as for the detail), and removes the session and its turns in one transaction, in any status: planning, created, live, completed or aborted. The stored feedback is a column of the session and goes with it. The quota is not refunded (D64), so a deleted session still counts for the day, and the seeker's active-session slot is free at once. A delete is final: a repeated delete is a 404 `INTERVIEW_NOT_FOUND`, like any other request for a deleted session, and it changes nothing. If the deletion fails the transaction is rolled back, the session and its turns are still there, and the answer is the sanitized 500. There is no audit record and no tombstone. **Deleting a live session only removes its rows: nothing in S4.4 notifies or disconnects a LiveKit agent or cleans a room, and the agent's next event for that session is refused by the ingestion as a 404 `INTERVIEW_NOT_FOUND`, which an M5 agent must treat as a reason to stop and disconnect.** It makes no model call and works after the AI consent is withdrawn. The tests of S4.4 are `backend/tests/test_interview_api_detail.py`, `backend/tests/test_interview_api_end.py`, `backend/tests/test_interview_api_delete.py`, the cases that every route of a session shares in `backend/tests/test_interview_api_session_common.py` (a table that each route of S4.4 joins), and the stage lists of `backend/tests/test_interview_api_contract.py` and `backend/tests/test_interview_api.py`. **The 405 of the interview paths** lists every method of the path in `Allow`: `DELETE, GET` for `/api/interview-sessions/{session_id}`, which has two routes, and the one method of every other interview path. FastAPI keeps one route per method and hands a request with a wrong method to the first route that matches the path, which advertises only its own method (and registering the other route first only swaps them), so the interview router is created with `route_class=all_methods_route_class()` from `backend/app/core/allowed_methods.py`: a route class that records the methods of its router's routes by path and widens the `Allow` of the 405 that the framework raises, in a fixed (sorted) order, and changes nothing else. Supported requests, the body and the other headers of the 405, the OpenAPI document and the no-store header are as they were, and an unrelated router keeps the framework's behavior. Its tests are `backend/tests/test_allowed_methods.py`, and the `Allow` tests of `backend/tests/test_interview_api_contract.py` (every interview path against its OpenAPI methods) and `backend/tests/test_interview_api_session_common.py`. **S4.5** registers the last of the seven seeker routes, `POST /api/interview-sessions/{session_id}/feedback` (get-or-create; there is no separate GET), which calls only `interview_feedback_service.ensure`. The answer is 200 for every result, as `FeedbackOut`: `report` (the stored or provisional report exactly as the service's `to_data()` made it, typed field for field by `FeedbackReportOut`; no field is added), `final`, `limited`, `reason`, `generated_at` and `notice` (`AI_NOTICE`). It has no `prompt_version`, no `attempts_used`, no second `method` and no lease data, and the report has no score, ranking, verdict or weight. The route adds one thing to the service: the `Retry-After` header of the busy 409 (D67 (6)), equal to `retry_after_seconds` and made with the application's own AppError handler, so the body is the handler's; every other error is the handler's, as everywhere. **What a request can give**, in the service's order (the HTTP tests drive each one with a mocked model): a stored report (final, no model, no quota, readable after the AI consent is withdrawn); 409 `AI_CONSENT_REQUIRED` for a new generation without the current AI consent, provisional and rules reports included; 409 `INTERVIEW_NOT_ENDED`; 409 `INTERVIEW_PLAN_INVALID` for a plan with no safe view; a provisional rules report (`reason` `plan_invalid`) when the digest does not match; the rules report stored as final in rules mode, for a session with no answers, or when the attempts are used up; 409 `INTERVIEW_FEEDBACK_BUSY` while another request holds the lease (`INTERVIEW_FEEDBACK_LEASE_SECONDS`); a provisional rules report with `limited` true and `reason` `quota` when the day's feedback-model quota is used up, with nothing kept. When the model is asked, it is called once, with no transaction open, after the lease, the attempt and the reservation were committed together: a usable report is stored as final (`llm:<model>`); a failure on an attempt below the cap gives a provisional rules report (`model_failed`), keeps the attempt and the reservation and frees the lease; a failure on the last attempt stores the rules report as final, and a further call is never made; a worker whose lease was taken over returns the winner's stored report or, if there is none, its own report as provisional (`lease_lost`), and never overwrites or releases the newer lease; a session deleted during the call is a 404 with the reservation still spent; an unexpected error is a sanitized 500 that frees the lease and keeps the attempt and the reservation. A model reply is validated by the existing pipeline: a quote must appear exactly in a masked candidate line of the same topic, a sentence that scores, ranks, judges or speaks for the company is dropped, and a reply with nothing usable counts as a failure. The tests are `backend/tests/test_interview_api_feedback.py` (the foundation and the outcomes that need no model) and `backend/tests/test_interview_api_feedback_model.py` (the model-backed outcomes, the transaction order and the privacy checks). The races run on one SQLite connection with a second database session as the other request, so they show the logic and not parallel requests, which only the PostgreSQL tests of the service cover (they are skipped without a database). **Processor caveat (Q35, open).** In model mode (`AI_MODE=llm` with a key) the model call of this route sends the PII-masked transcript text of the two safe views (never the CV, the PDF, the display name or an email) to the processor behind `ai/llm/client.py` (an Anthropic client in the code today). The transcript consent text (D65) does not name any processor, and Q35, which asks whether the processors of the practice interview need a legal check and a notice that names them, is unresolved; its text lists Groq and LiveKit, not the provider of this model call. This paragraph describes the caveat. It is not a legal approval and it does not resolve Q35, and the model-backed feedback is not to be treated as ready for production use until Q35 is decided; in rules mode nothing leaves the backend. With S4.5 all seven seeker routes of D67 exist. **M5 S1 (D80)** adds the two internal agent routes (context, events) and the agent's authentication (`core/agent_auth.py`: the shared secret and the room binding); see §4.1. Q24, Q35 and Q39 are open, and the PostgreSQL behaviour of the services is unverified (see the limits above).

**Fit** = Σ(weight × score) / Σweight, rounded to 1 decimal (`ai/scoring/fit.py`). Ranking: Fit ↓, then more criteria ≥ `STRONG_SCORE`, then earlier application. LLM criteria run in parallel (up to 4 threads).

The only criteria read path for scoring is `criteria_service.load_for_scoring()` (drops criteria blocked by a newer blocklist and rescales weights).

**Cost.** Only LLM calls cost money, and only with `AI_MODE=llm` (`LLM_PROVIDER=groq` default for demo or `anthropic`, D91): CV structuring (1 call per upload), JD analysis (1 per click), source criteria previews (at most `COMPANY_DAILY_LLM_PREVIEWS` per company per day, D89), JD drafts (1 per click, at most `JD_DAILY_LLM_DRAFTS` per company per day), recruiter verification questions (at most `COMPANY_DAILY_LLM_VERIFICATIONS` per company per day, D89), roadmaps, interview questions and CV reviews (1 per new result, cached, together at most `CAREER_DAILY_LLM_GENERATIONS` per seeker per day), `project`/`other` criteria (1–2 per criterion per application). ### 6.1 Recommendation

Decided parts: docs/DECISIONS.md D1–D3 (D1 replaced by D42), D15, D16, D42, D43, D18–D20. Job recommendation (`services/recommendation_service.py`) and talent recommendation with offers (`services/talent_service.py`, `services/offer_service.py`) are implemented. Core rule: the company's `job_criteria` are used **the same way** for applicant scoring and for recommendation, and `evaluations` (keyed by job × CV version) are reused.

**Job recommendation (seeker → jobs)**

- Candidates: published, unexpired jobs. Excluded: jobs already applied to; seekers with no confirmed CV or no AI consent.
- **Pref** (0–100, `ai/scoring/pref.py` `pref_score`; docs/DECISIONS.md D15) = mean over the preference fields the seeker **filled in**, each 0 or 100: desired locations (match when equal or one contains the other, e.g. "서울" (Seoul) ⊂ "서울 강남구" (Seoul Gangnam-gu)), employment types (job's type in the list), role keywords (any keyword in the job title or JD; a keyword starting or ending with a Latin letter or digit must sit on a word boundary there, so "Java" does not match "JavaScript"). Compared after whitespace/case normalization; synonyms stay open ([Q25](docs/DECISIONS.md#3-open-questions)). With 1 field filled Pref is 0/100, with 2 it is 0/50/100, with 3 it is 0/33.3/66.7/100, so "≥ 40" means at least half of the filled fields match. The result also lists matched and missed fields.
- **Empty preferences**: an empty field is not counted. A seeker with no preferences has Pref = 100 for every job, so ranking is by Fit alone and the evaluation cap below is what limits cost. Planned: show a "희망 조건을 입력하면 추천이 정확해집니다" ("Enter your preferences for more accurate recommendations") prompt on the page when all three are empty.
- **Fit**: reuse the evaluation for (job, newest confirmed CV version); create it if missing. Fit is computed only for jobs with Pref ≥ 40, to limit LLM calls.
- **Evaluation cap**: one recommendation call queues at most `RECO_MAX_NEW_EVALUATIONS` (10) evaluations (new or re-queued), picking candidates with the highest Pref first, then newest `published_at`. Jobs over the cap are left out of this response and get evaluated on later calls.
- **Daily cap per seeker** (**only in `AI_MODE=llm`**, D16): at most `RECO_DAILY_NEW_EVALUATIONS` (30) queued evaluations per seeker per day (KST), so reloading the page cannot bypass the per-call cap. Counting rule and re-queues: see the next bullets (uses `queued_at`); evaluations queued by applying do not count. When the cap is reached, the call returns only existing `done` results. Talent recommendation has its own per-company limit (`TALENT_DAILY_NEW_EVALUATIONS`, D19, [issue 26](#11-known-issues-and-risks)). Both endpoints are covered by [issue 22](#11-known-issues-and-risks). Further option if cost is still high: turn recommendation on only when at least one preference is filled.
- **CV versions:** evaluations are keyed by job × CV version, so a newly **confirmed** CV version cannot reuse old evaluations and is re-evaluated (within the cap). This is a deliberate trade-off: scores always match the CV the seeker confirmed. Saving an edit without confirming creates no evaluation, because recommendation uses only the newest confirmed version.
- **Get-or-create rule** (implemented for apply, retry, job recommendation and talent recommendation; new queue paths must follow it): always obtain the evaluation through `evaluation_service.ensure(job_id, cv_profile_id)` (unique on job × CV version), never create one directly. `ensure()` must catch `IntegrityError` on insert (inside a savepoint), roll back that savepoint and re-read the row, so two concurrent requests end up with the same evaluation instead of a 500. Queue scoring **only** when the evaluation is new, `failed`, or `pending` for longer than `EVALUATION_STALE_MINUTES`; a fresh `pending` one is left alone because a task is already running. Implemented as `evaluation_service.claim()`: one conditional `UPDATE … WHERE status = 'failed' OR (status = 'pending' AND (queued_at IS NULL OR queued_at < now − EVALUATION_STALE_MINUTES))`, so of several concurrent requests exactly one queues. A concurrent apply by the same seeker gets 409 `ALREADY_APPLIED` (unique `applications(job_id, seeker_id)`).
- **Columns for the rule above:** `evaluations.queued_at` (set on every queue) and `evaluations.attempts` (incremented on every queue). Every queue path (apply, retry, job recommendation, talent recommendation) must set both; the stale check uses `queued_at`, because a re-queued evaluation keeps its old `created_at`.
- **Re-queues count toward the caps**: every queue — new, `failed` or stale `pending` — uses one slot of `RECO_MAX_NEW_EVALUATIONS` and of `RECO_DAILY_NEW_EVALUATIONS` (daily count = the seeker's evaluations with `queued_at` today that no application references). Recommendation stops re-queuing an evaluation after `EVALUATION_MAX_ATTEMPTS` (3) attempts (`claim(max_attempts=…)`); it then stays `failed` and recommendation skips it. `attempts` is reset to 0 when the seeker applies to that job or the company clicks 다시 분석 (Re-analyze) (both queue it again and are not limited by this count). A newly confirmed CV version is a new evaluation, so it starts at 0. Editing the job does not reset it: after publishing only weights can change, and weights do not need re-scoring.
- **Fencing** (implemented in `evaluation_service.evaluate`): the background task receives the `queued_at` value it was queued with. Before writing scores it updates the row only `WHERE id = :id AND queued_at = :token` (or re-reads it under `SELECT … FOR UPDATE`); if no row matches, a newer queue has replaced it, so the run discards its results and exits without changing `status`. This stops an old, slow run from overwriting the result of a newer one.
- **Concurrency**: calls by the same seeker run one at a time (`SELECT … FOR UPDATE` on the `users` row), so parallel calls cannot overrun the caps; `claim()` keeps one evaluation from being queued twice.
- **Sync vs background**: new evaluations run in the **background** (same `evaluation_service.run_in_background` as applying); the call never waits for scoring. The response lists only jobs whose evaluation is `done`, plus `"pending_count"` so the page can show "분석 중 N건" ("N being analyzed"). **Retry of `pending`:** nobody clicks 다시 분석 on the seeker side, so the next recommendation call re-queues its own `pending` evaluations older than `EVALUATION_STALE_MINUTES` (10, same rule as issue 2) and `failed` ones, still within the cap. Evaluations shared with an application keep the company's 다시 분석 path too.
- **Final** = 0.5·Fit + 0.5·Pref; recommend only when Fit ≥ 40 **and** Pref ≥ 40.
- Order: ① filter candidates → ② Pref, drop < 40 → ②b required criteria gate (D50, `gate_service`), drop FAIL → ③ load `done` evaluations; queue missing/stale ones up to the cap → ④ Fit with current weights, drop < 40 → ⑤ Final → ⑥ sort by Final ↓, then Fit ↓, then newest `published_at`, top `limit`.
- What seekers see (D42, D43): the **match score** = Final rounded down to an integer, with the band 매우 적합 ≥ 80 · 적합 60–79 · 참고 40–59 (rounding down never changes a band; below 40, possible only on the job list and detail, the number has no band); the **preference score** (Pref rounded down); one score per criterion **category** = plain mean (no weights) of the job's criterion scores in it, rounded down; on the job detail page each criterion's score. Never weights, Fit as its own number, `reason` or `evidence`, and never a score for a job the seeker applied to. `GET /api/recommendations/matches` and `GET /api/jobs/{job_id}/match` read existing `done` evaluations only and never queue one. Matched/missing skills come only from the roadmap (D21).

**Talent recommendation (company → seekers)**

- **Prerequisites (D18):** [issue 3](#11-known-issues-and-risks) fixed (rule scores and what companies see come from the masked text); [issue 6](#11-known-issues-and-risks) mitigated for the demo by re-queuing stale `pending` evaluations (a separate worker comes after the demo); [issue 26](#11-known-issues-and-risks) handled by the caps below; [issue 24](#11-known-issues-and-risks) reduced (see the anonymous profile).
- **Access rule (all company-side APIs):** a company may read an evaluation, score or profile only for (a) seekers who applied to one of its jobs — today's behaviour, enforced through `get_owned` on the application — or (b) seekers with `profile_public = true` **at the time of the request**, and then only the anonymous fields below. Evaluations created for job recommendation are otherwise never visible to companies. Check `profile_public` on every read, not only when listing, so turning it off takes effect immediately.
- Candidates (D19, `services/talent_service.py`): `profile_public = true`, AI consent at `RECO_MIN_CONSENT_VERSION` or later, and a newest CV version that is confirmed, checked on every request. Excluded: seekers who already applied to that job, seekers with a `pending` or `accepted` offer from that company (any job), and seekers who `rejected` the company's offer for this job (re-offer rule, issue 23).
- Pref ≥ `RECO_MIN_PREF` filters first (the seeker's preferences against the job), then the required criteria gate (D50: FAIL left out before any evaluation is queued; the offer check uses the same `talent_service.gate_allows`), then Fit ≥ `RECO_MIN_FIT`. Ranked by Fit, then more criteria ≥ `STRONG_SCORE`, then newest `profile_public_at`.
- **New evaluations**: same queue rules as job recommendation (`claim(max_attempts=EVALUATION_MAX_ATTEMPTS)`, background only). At most `TALENT_MAX_NEW_EVALUATIONS` (10) queues per call, always; at most `TALENT_DAILY_NEW_EVALUATIONS` (30) per company per day (KST) only in `AI_MODE=llm`, counted generously as every evaluation of the company's jobs queued today that no application references (the seekers' own job recommendations count too). Highest Pref first, then the most recently confirmed CV. Calls of one company run one at a time (`SELECT … FOR UPDATE` on `companies`). The response lists `done` results plus `pending_count`.
- Anonymous profile — shown: anonymous ID (`"C-"` + HMAC of company and seeker: stable within a company, different across companies), skills found in the CV text, experience in whole years (`verified_experience`, rounded down), experience roles (only when their `source` line is in the text), technologies found in the 프로젝트 section, degree and major (verified the same way), certificates, desired location/employment type/role keywords, Fit and per-criterion `score` and `level` for that job, and the latest offer status from this company. No minimum pool size. Hidden: `display_name`, email, user/CV ids, school name, org names, project names and descriptions, dates, `summary`, CV text, and the per-criterion `reason` and `evidence` — evidence quotes CV lines and reasons paraphrase them, which leaks text and makes re-identification easier ([issue 24](#11-known-issues-and-risks)). `reason`/`evidence` become visible only through the normal applicant view after the seeker applies.
- Offers (D20, `services/offer_service.py`): the company sends one to an `anonymous_id` for one of its published jobs, with an optional `message`; the seeker must pass the same rules as the talent list. One live offer per (company, seeker): a `pending` (not expired) or `accepted` one blocks a new offer for any job (issue 16, checked in the service under a `FOR UPDATE` lock on `companies`, no DB constraint). After `rejected` the company cannot offer the same job again; another job is fine; `cancelled` blocks nothing (issue 23). At most `OFFER_DAILY_LIMIT` (20) offers per company per day (KST). A `pending` offer expires `OFFER_EXPIRY_DAYS` (14) after `created_at` (computed, shown as `expired`). Accept, reject and cancel are each one conditional `UPDATE … WHERE status = 'pending'` and not expired, so of two concurrent answers one wins. Contact (`display_name`, email from `users`) is returned **only after `accepted`**.
- **Leaving the pool with a pending offer** (former Q10, decided in D20): turning `profile_public` off or withdrawing AI consent keeps the offer answerable for the seeker; the company keeps the `anonymous_id` but no longer sees the anonymous profile (`candidate: null`). An accepted offer keeps its contact details.

**Consent:** `CONSENT_VERSION` is `2026-10-13`; recommendation requires `consent_version ≥ RECO_MIN_CONSENT_VERSION` (`2026-10-13`), else 409 `AI_CONSENT_REQUIRED`, so users who consented to an older version get no evaluation for jobs they did not apply to. Apply and CV upload need AI consent but not the newest version; existing applications stay valid. Users re-consent with `POST /api/users/me/consent`; `/api/users/me` tells the frontend when (`consent_required`). A seeker may withdraw AI consent (`DELETE /api/users/me/consent/ai`): every new AI use of their data stops (CV upload, apply, recommendation, the company's 다시 분석), they leave the talent pool, stored data stays, and a run queued before the withdrawal is not cancelled (D17). The frontend has the re-consent screen (`/consent`, §5); its consent text names "지원 평가와 맞춤 공고 추천" ("application evaluation and personalized job recommendation") and is still marked as a draft (`auth.consent.draftNote`). Appearing in talent recommendation additionally requires the separate `profile_public` opt-in (`profile_public_at` records when).

**Evaluation (AI quality) plan [Planned]:** synthetic data only — 20 synthetic CVs + 5 jobs with hand-made answers. Metrics: extraction precision/recall, quote-verification pass rate and evidence review, top-5 agreement of Fit ranking vs hand ranking, processing time (`POST /api/cv` → response; apply → `done`), failed-evaluation and upload-error rates. Each measured for rules-only and LLM mode.

**Plan.** Deterministic: the same inputs give the same plan whatever order the criteria arrive in. Criteria come with the importance label (핵심 / 중요 / 일반) only, never a weight. Order: an optional warm-up built from a verified line of the candidate's own CV (`depth` null), the criteria by importance and then by their position in the job, and one behavioral question last (`depth` null). `build_plan(..., depth=2)` selects one question per criterion in candidate order: bank question at the requested depth → template at the requested depth → nearest alternate depth (`2` first, then the other) checking bank then template → untagged bank item → neutral fallback (D93). `InterviewPlan.depth` and `PlanItem.depth` persist inside the plan JSON (legacy stored plans without those keys load as plan depth `2` and item `depth` `None`). The number of questions is capped (D57); a 핵심 criterion outranks the warm-up, and a criterion with no slot or no question that passes the screens is listed in `plan.uncovered` (status not_asked), never dropped silently. At most 4 criteria can be 핵심 (`IMPORTANCE_HIGH` is `25` and the weights total 100), so with the default cap they all fit next to the behavioral question. Every question has 2–4 rubric points, taken from the criterion's own description where it gives enough and otherwise generic for its category; they are marked AI-generated expectations (`source`, `rubric_notice`), not company requirements.

**CV boundary (`cv_context.py`, `sensitive.py`, D62).** The stored masked CV still carries age, gender and military-service text ([Q24](docs/DECISIONS.md#3-open-questions) is unresolved and `mask_pii` is unchanged), so the interview never reads it directly. `clean_cv` makes the version it may use (since D85 it lives in `ai/guardrails/cv_clean.py`, with its vocabulary in `ai/guardrails/sensitive.py`, and the recruiter verification questions use it too; the interview package takes it only through `cv_context.py`), in steps that do not depend on one another. (1) Structure: only text under a known section heading is kept, so the header before the first heading (name, contact and personal lines) is dropped. A heading that looks personal starts a block that is dropped up to the next known heading. It is matched by prefix (인적사항 (personal details) and 병역사항 (military-service details) with any suffix such as "(필)", "Personal Profile", "Military Service Record") or, as a catch-all that often holds such lines, as a whole heading (기타 (other), 추가 정보 (additional information), 취미/특기 (hobbies and skills), "Others", "Family"). It fails closed: a heading that looks personal is treated as personal, with "Personal Projects" as the one deliberate exception. (2) Labels: a personal label (성별 (gender), 생년월일 (date of birth), 국적 (nationality), "Date of birth", "Nationality", …) is dropped with its value, whether the value is on the same line or on the next short line, and a run of labels takes as many value lines. (3) Segments: a parenthesis or a ` | ` segment that matches the vocabulary is cut and the rest of the line stays ("학사 2015.03 ~ 2021.02 (군 휴학 2017~2019)" keeps school and dates). (4) Vocabulary: what still matches is reduced to its other clauses or dropped. The vocabulary covers digits, spoken numerals and decades for age, gender words and words that state it, and military status, branch, rank, unit, specialty, discharge, exemption and alternative-service terms in Korean and English; it skips compounds such as 3세대 (third generation), 세션 (session) and 전역 변수 (global variable). A CV with no known heading gives nothing. `CleanCv.removed` keeps the removed lines (10 characters or more), so a plan can be checked for a removed line that came back in a question, a quote or a rubric point. Over-blocking is accepted: a sentence about 연령대별 추천 (recommendation by age group) is kept, one with 성별 is not. A test makes `cv_context.py` the only module of `ai/interview/` that reads the stored CV: any other module may import only a short list of line-level helpers from the CV-related packages (`heading_key`, `has_content`, `keywords` and similar), and a parameter that carries the stored CV (`masked_cv`, `cv_text`, `masked_text`) may only be handed to `clean_cv` or `validate_plan` (or compared with `None`). That guard does not see a reader that takes the CV under another parameter name, or one outside `ai/interview/`.

**Plan validation (`validate.py`, D61).** `validate_plan` is the last step of `build_plan` and the first step of `InterviewEngine.__init__`, so a plan from the builder, one built by hand and one loaded with `InterviewPlan.from_dict` are checked by the same function before anything is spoken or sent. Nothing in a plan is trusted. A question or rephrase must pass `screen_spoken` and contain no removed CV line, or the item is dropped (a criterion item is then listed in `plan.uncovered`) or the generic rephrase is used. Intent, tips, rubric points, keywords and the criterion name must not match the vocabulary or the blocklists or contain a removed CV line; what fails is dropped, and a failing rubric is replaced by the generic one of its kind. Ids, kinds, depth bounds (`1`–`3` on the plan, `1`–`3` or `None` on criterion items, `None` on warm-up and behavioral) and importance labels are checked, so a forged plan cannot carry an unknown topic, an out-of-range depth or a weight. `cv_quote` is kept only when the CV text is passed and the quote is found in the cleaned CV, so the realtime agent, which has no CV, runs without quotes. Validation is idempotent and reports codes (`engine.plan_issues`), never text. The question bank is not trusted either: `build_plan` screens each bank question (text, intent, tips, quote) before choosing it, and the company's criterion names and descriptions are cut the same way before the rubric and the keywords are made. **The removed-line check and the `cv_quote` check depend on the CV text being supplied.** `build_plan` always has it; `InterviewEngine(plan, …, cv_text=…)` takes it as an option. Without it, the format checks, the vocabulary and the blocklists still apply, but nothing can show that a text is not a removed CV line, and every `cv_quote` is dropped. The realtime agent (M5) has no CV text, so its engine runs without quotes and without the removed-line check (the backend validated the plan with the CV text when it built it). With the CV text, the removed-line check still needs a verbatim match of 10 characters or more, so a paraphrase of a removed line is not caught.

**The candidate's own words (D59, D61).** A disclosure the candidate volunteers is cut from every model input (the turn analysis, `previous` and `asked` of the next turn, the planning and rubric requests, the views) by the same vocabulary, sentence by sentence and then clause by clause, so "저는 27살이고 Java로 API를 개발했습니다" keeps its second clause. Clauses are split after 고, 며, 서, 면, 는데 and 지만, at commas and semicolons, and at "but", "while" and "because" (not at "and", which also joins "Kotlin and Java"); a flagged parenthesis is cut first. A quote that matches is not kept as evidence, a suggested follow-up that matches is dropped, and a mixed sentence gives no quote. The stored transcript keeps the words as said, masked for personal data: it is the candidate's record, not model input.

**Model-input boundary (`boundary.py`, `views.py`, D61).** Everything the interview sends to a model is a `ModelInput`: made only by `compose` from `SafeText` parts (text that `for_model` leaves unchanged; the constructor refuses anything else) and sent only by `ask`. This covers the turn analysis (`prepare_turn`), the rubric request, the planning prompt (`make_bank` gives the D21 planner a `GatedClient`, which cuts every line of the prompt the planner builds as text) and, later, the feedback. The feedback generator (M3) reads an interview only through `transcript_view` and `plan_view` (which return `SafeText`), and later code must do the same. That is enforced only in part: tests let only the engine, the state and the views read `state.turns` and `state.plan` inside `ai/interview/`, and keep model-input and feedback code free of raw serialization. `state.to_dict()` (and `InterviewPlan.to_dict()`) is raw: it holds the transcript as the candidate said it, it is for persistence, and it is not an approved model-input interface. The realtime agent (M5) makes its own call and must explicitly send only `ModelInput.system` and `ModelInput.user` to its model; nothing enforces that yet, and since M5 S2 the scans include `interview_agent/` (D80). M4 must plan with `make_bank` (the cleaned CV and a gated planner prompt), not with `make_questions` on the raw CV, which the D21 job-page feature still does; `validate_plan` is the backstop, and no test forces the choice. What the boundary guarantees: text that reaches a model through it has had everything the vocabulary matches left out and angle brackets neutralized, and no raw string can be wrapped as `SafeText`. What it does not: it cannot recognize a disclosure the vocabulary does not know, and it cannot see a model call made another way.

**Architecture tests (`ai/tests/test_interview_model_boundary.py`).** AST scans of `ai/` and `backend/app/` list every file that refers to `complete_json`, takes a client from `ai_runtime.llm()` or `get_llm_client`, or imports a model SDK, and fail when a new one appears. They fail if a file that imports the interview package calls a model itself. Inside `ai/interview/` they fail if a module other than the boundary calls a model or builds a `ModelInput`, if a module other than the engine, the state and the views reads `state.turns` or `state.plan`, or if an unlisted module calls `compose`. Since M5 S2 they scan `interview_agent/` too: its one Groq client (`turn_model.py`) imports neither the interview package nor the backend, and only its runner sends a `ModelInput` (D80). They are a review gate, not a proof: they see imports and attribute names, not a call built from strings at run time, and not code outside the scanned directories. The existing seeker features (CV structuring, scoring, CV review, the D21 job-page questions, the JD and roadmap features) are listed as known call sites and are unchanged. Two more guards (D62): the stored-CV reader guard above, and a guard against raw serialization. The latter scans the listed modules (`llm.py`, `boundary.py`, `cv_context.py`, `views.py`, a future `feedback.py`), the `TurnContext` class and any function in `ai/` or `backend/app/` that calls a model-input builder, for `to_dict`, `asdict`, `vars`, `__dict__`, `json.dumps`, `model_dump` and the `str` or f-string of the state, a plan or the turns. Persistence code (the engine, the state, the types, a backend service that stores a session) is not restricted and may serialize. A run-time tripwire calls every model-input builder with `to_dict` and `dataclasses.asdict` set to raise, for what a scan cannot see (a `getattr`, a helper in another module).

**One answer, one decision** (`decide.py`; the first rule that applies wins):

1. Not enough time left → wrap up (the answer is still recorded).
2. Nothing said → clarify once, then skip the item. Very little said, with no content in it → ask for more once, then take it as given (not_shown, never skipped; D59).
3. Request to repeat or explain → repeat or rephrase once, then skip.
4. Off topic → redirect once, then skip.
5. "Don't know" → mark not_shown and continue.
6. Partial answer with a rubric point still missing → follow up on the highest-priority missing point while the follow-up budget lasts.
7. Otherwise → the next item.

The clarification budgets are independent (D59): at most one interviewer-initiated clarification per question (asking again, asking for more, redirecting) and at most one candidate-requested repeat or rephrase per question. Length is a soft heuristic: a short answer with a content cue ("자바요", "멱등성이요"; skill names count with their Korean aliases) is analysed like any other. Silence: one nudge per item after the nudge time, a skip after the skip time. Topic statuses: not_asked, asked, demonstrated, partial, not_shown, skipped.

**Guards.** Every spoken line passes `screen_spoken`: no URL, email, placeholder or code, no verdict word, nothing about age, gender or military service (D62), nothing either blocklist matches (the criteria guardrail and the interview blocklist, through `career/interview.py`). A repeated question is prevented: exact repeats for template lines (two templates that differ only in the criterion name are two questions), fuzzy repeats for wording a model chose freely. Any analysis, from the rules or later from a model, goes through `sanitize_analysis`: unknown rubric points and quotes that are not in the masked answer are dropped, and a suggested follow-up is kept only if it passes the screens and repeats nothing. An answer the rules classify as empty, very short or a request to hear the question again is never overruled by a model, and a model cannot claim one either.

**Model layer (`llm.py`, D52, D54, D59).** Nothing here calls a provider: the caller asks the model (the backend through `LLMClient`, the agent through its own call, within `INTERVIEW_TURN_LLM_DEADLINE_SECONDS`) and this layer prepares and checks. `prepare_turn` builds a `ModelInput` from `engine.turn_context()` and nothing else, with what the vocabulary matches left out and angle brackets neutralized (see the boundary above); it returns nothing, so no model is asked, when the rules already classify the answer as empty, very short or a request to hear the question again. A model may answer only in `TurnLlmOut`: answered, partial, off topic or don't know; a level for every rubric point; at most two verbatim quotes; one follow-up. `parse_turn` rejects the whole answer, and the rules decide the turn, on invalid JSON or schema, an unknown, duplicate or missing rubric id, an inconsistent answer type, or any quote that is not in the answer; a follow-up that fails a screen is dropped on its own and the template speaks instead. The prompts are `ai/prompts/v1/interview_turn.md` and `ai/prompts/v1/interview_rubric.md`, new files; no existing prompt changed. Nothing calls `rubric_request` / `parse_rubric` yet: plan-time rubric enrichment is a later step.

**Final feedback (`feedback.py`, D63).** `make_feedback(transcript, plan, resources=…, skills=…, blocklists=…, llm=…)` writes the report the seeker reads after the interview. It takes the outputs of `transcript_view` and `plan_view`, or of `transcript_view_from` and `plan_view_from` rebuilt from what a backend persisted (the turns, the plan the engine ran, and `coverage_snapshot(state)`, which holds codes only). It refuses interview state, an engine and raw turns with a `TypeError`, it reads no CV, and it does not use `find_gaps`, which does. **Report.** `method` (`rules` or `llm:<model>`); `topics`, each with its engine-owned status and its importance label; `strengths` (a sentence and one or two quotes); `gaps`; `improvements`; `practice_questions`; `resources` (title and URL); `uncovered` (criteria that got no slot); fixed `notes` (no answers, stopped early, out of time); `rules_sections`; and the notice that rubric points are AI-generated. The report has no number that scores, ranks or counts, no verdict and no hiring advice, and its types have no such field. **Rules report.** Always computed first; deterministic; no key. A strength for each demonstrated or partial topic that has a stored quote found in the candidate's lines, worded from the rubric points the answers showed; gaps from the rubric points not shown, from skipped topics and from topics not covered; fixed advice chosen by the statuses present; practice questions from rubric templates (`rules.fallback_question` for a criterion with none). At most four strengths, four gaps, four improvements and three practice questions, 핵심 (core) topics first. **Model path.** One request at most, made by `compose` from SafeText lines (the plan with the engine's statuses, the rubric levels, the questions already asked, the transcript with topic ids; the earliest turns that fit in 12000 characters) and sent by `ask`. No request when there is no question or no answer. The model answers in a strict JSON object with four lists; it cannot set a status, add a field or give a URL. **Evidence.** A strength needs one or two quotes of 8 to 120 characters that appear exactly (whitespace collapsed, same case) in one candidate line of the same topic, and its topic must be demonstrated or partial. An interviewer line, another topic, a changed word, a shortened or paraphrased quote and a placeholder do not count. A strength without a verified quote is dropped, and nothing else is affected. **Sentences.** Every sentence passes the spoken-line screens (URL, email, placeholder, code, verdict word, the age, gender and military-service vocabulary, both blocklists), a score screen (a number followed by a unit such as 점 (points), % , 개 (items) or 명 (people), a rank, a grade, a comparison with other people, a hiring word) and a question screen (a statement may not be a question). It may name no technology or certification, by Latin name or through the skill dictionary, that is not in the plan or the candidate's own lines, and it may not talk about the company, a requirement or an expectation (a conservative word screen: it cannot tell a true statement about a requirement from an invented one, so it refuses all). A failing sentence is dropped on its own. **Practice questions.** A model suggestion is kept only if it is screened, grounded in the name, question or rubric of the topic it names, and not a repeat of a question already asked or of another suggestion; if none is kept, the rubric templates are used. **Links.** Looked up in the code, never taken from the model: the skill and certificate names in the criterion text of the plan, for the topics with a gap, in `data/learning_resources.yaml` only (an entry marked `verified: false` is never returned); none for the warm-up or the behavioral topic, whose text is not about a skill the job asks for. **Fallback (D54).** No client, a failed call (any exception), invalid JSON, an invalid schema or no usable item gives the rules report unchanged (`method` is `rules`). When the model has usable items, a section with none falls back to the rules section for that section only, `method` is `llm:<model>`, and `rules_sections` names those sections. **For M4.** Persist `engine.state.plan` (the plan the engine ran: the item index of a turn points into it), the turns and `coverage_snapshot(state)` at the end of the session; rebuild with `plan_view_from(plan, snapshot, blocklists=…)` and `transcript_view_from(turns, plan_view.topic_ids)`; add the `AI_NOTICE` to the response; show the report to its owner only (D53). Not built: the endpoint, the response schema, storage and expiry. **Limits.** The screens are a vocabulary and token rules, not understanding: a fluent sentence can be wrong, and a disclosure the vocabulary does not know is not caught (see Known limits). The grounding of a practice question is a shared content word, not meaning, and the check for an invented technology sees names; a claim about what a job wants is caught only by the word screen. A quote of a sentence the sanitizer cut cannot be used, so a topic whose answers were cut has fewer strengths. A persisted plan that is not the one the engine ran can shift the topic of a turn; `SafePlan.issues` shows when validation changed it. The rules report judges cue words. The size limits are defaults, not decisions. The model's wording quality is unmeasured.

**Privacy.** `on_answer` masks the transcript first and stores only masked text and counts of what was masked. `turn_context` masks again, so even a raw transcript handed to it cannot put personal data into the model input. The stored transcript keeps the candidate's words as said (masked); `views.transcript_view` is its model-safe form. `spoken_pii.py` reuses the placeholder tokens, the surname list and the account-name patterns of `parsing/pii.py` (D39) and adds what only speech has (spoken digits and emails, "저는 …입니다" introductions). It does not call `mask_pii` as a whole: that would mask everything after the word 주소 and look for a name at the top of the text. Best effort: a name said without any introduction is not found.

| Wrap-up reserve                                                                            | 45 seconds               | [Recommended]; engine default, not part of D57               |
| "Too short" answer | under 8 characters or 3 words, and no content cue in it | [Recommended]; a soft heuristic only, never a reason to skip by itself (D59) |
| Similarity that counts as a repeat (model wording only)                                    | 0.8                      | [Recommended]; engine default                                |
| Feedback report size limits                                                                | 4 strengths, 4 gaps, 4 improvements, 3 practice questions, 4 links | [Recommended]; engine defaults of `feedback.py`, not decided by D63 |
| Feedback transcript cap                                                                    | 12000 characters sent to the model | [Recommended]; the earliest turns that fit, and the quote check uses exactly those |
| Feedback quote length                                                                      | 8 to 120 characters      | [Recommended]; evidence is a phrase, not a word              |

The first group lives as constants in `ai/interview/types.py` (`InterviewLimits`); M4 adds backend settings that start from these defaults (see [§9](#9-environment-and-configuration)).

**Exception to AI rule 2 (D52).** `ai/llm/client.py` stays the only LLM gateway of the app. The one exception is the Interview Agent's per-turn analysis, which may call Groq with text the engine has masked; planning and feedback use the gateway. `CLAUDE.md` rule 2 names this exception and says that it covers LLM text-generation calls only, not the speech services of the agent (D83; those are D80 and Q35).

**Known limits.** The rules judge cue words, not correctness: they tell the seeker what they found, nothing more. Spoken masking is best effort. The age, gender and military-service cut is a vocabulary plus the CV structure, not understanding, and it is not a guarantee. Known to pass: a disclosure that uses none of the terms (a euphemism, an indirect description of service or age, a pronoun such as "she" or "his" in English text, family words that are not in the list); what is left of a mixed sentence after the cut ("for the country for two years" without the word for service); a line about these topics under a normal heading, or in a block whose heading is not recognized as personal (an unrecognized non-personal heading such as "Volunteer Work" keeps its body); a value that is not on a short line next to its label; and a paraphrase of a removed CV line (the removed-line check needs a verbatim match of 10 characters or more). Over-blocking is accepted: a company line shaped like a personal heading (a short line alone that starts like 가족 (family)) drops the rest of its section. The stored CV still carries these topics, and the existing seeker features (CV structuring, scoring, CV review, the D21 job-page questions) still send them to a model: Q24 is unresolved and nothing here approves that. A plan keeps a `cv_quote`, and gets the removed-line check, only when the CV text is passed to the engine (the realtime agent's engine has none). `state.to_dict()` is raw and is not a model-input interface; reading an interview only through `transcript_view` and `plan_view`, M4 planning with `make_bank` and the agent sending only `ModelInput.system` and `ModelInput.user` are requirements for future code, not yet enforced. The architecture tests are a review gate: they do not see a model call built from strings, a stored-CV reader under another parameter name, or code outside `ai/` and `backend/app/`. The backend (M4) and the agent (M5) are not built; each will add model call sites, which the tests force to be listed. The feedback generator's own limits are in its paragraph above. The model's judgement quality is unmeasured, and `gpt-oss-120b` returning this JSON reliably is unverified.

## 7. Coding conventions

**Current**:

- Code, comments, commit messages: English. User-facing messages (errors, notices, AI comments): Korean.
- Python: `snake_case` files/functions/variables, `_private` helpers, `PascalCase` classes, `UPPER_SNAKE` constants. Pydantic models suffixed `In`/`Out`/`Create`/`Update`. Type hints everywhere (`X | None`, `Annotated`, `Mapped[...]`).
- Services: `services/<domain>_service.py`; routes: `api/v1/<domain>.py`.
- Endpoints that call synchronous code (DB, PDF, LLM) use `def`, not `async def`.
- Status values: string constants class (`JobStatus.DRAFT`) + DB `CHECK` constraint, no DB enum types.
- API: `/api` prefix, plural nouns, `me` for the current user's resource, verb sub-paths for actions (`/publish`, `/close`, `/analyze`, `/retry`).
- DB: plural `snake_case` tables; constraints `ck_<table>_<col>`, `uq_<table>_<cols>`, indexes `ix_<table>_<col>`.
- Errors: `AppError(status, CODE_UPPER_SNAKE, "Korean message", **extra)`.
- Logging: `logging.getLogger(__name__)`; warnings/exceptions on AI failures. No central config.
- Imports: stdlib → third-party → `ai.*` → `app.*`.
- Prompts: versioned Markdown under `ai/prompts/vN/`.
- Frontend: `PascalCase.tsx` components, pages under `pages/seeker/*` and `pages/company/*`, all HTTP through `src/api/client.ts`.
- Frontend UI text: never hardcoded in components; every string goes through `t(key)` from `src/i18n/` (source locale `src/i18n/ko.ts`, keys type-checked). A new language is one new file `src/i18n/<locale>.ts` (`export default { ... } satisfies Messages`); no other file changes.
- Commits: imperative, capitalized English sentence.
- Tests: pytest from the repo root; no DB, network or key needed (in-memory SQLite, hashing embedder, `FakeLLM`).

**[Recommended]**, not agreed: run `pytest` (and `npm run build` for frontend changes) before committing; add a linter/formatter (e.g. `ruff`).

1. *Environment.* Set it in the terminal that runs the commands (an IDE extension may not inherit variables from another terminal): `TEST_DATABASE_URL`, for an existing database also `TEST_DATABASE_EXPECTED_NAME` and `TEST_DATABASE_CONFIRM_DESTRUCTIVE`, `CAREERSYNC_DOTENV=0` and `AI_MODE=rules`. 2. *Preflight, from the repo root.* `python backend/tests/db_safety.py --no-connect` checks the URL and the environment only. `python backend/tests/db_safety.py` also connects once, read-only, and requires `current_database()` to be the approved name. Exit code 0 passes, 2 means a rule refused and 3 means the database could not be reached; anything but 0 stops the work.
3. *Run.* `python -m pytest <files>` from the repo root, one process at a time: the fixture wipes the one shared database, so never run two at once (no xdist). A run shows that the gated tests executed only when its summary has no skipped test and its passed count equals the collected count from `--collect-only -q`; on a URL that is not PostgreSQL the same tests skip.
4. *Restore.* The fixture leaves no application table and never touches `alembic_version`, so rebuild the schema: set `DATABASE_URL` to exactly `TEST_DATABASE_URL`, run `python backend/tests/db_safety.py --app` (it also requires that equality and `CAREERSYNC_DOTENV` to be `0`), then from `backend/` run `python -m alembic stamp --purge base`, `python -m alembic upgrade head` and `python -m alembic check`. Do not run `alembic downgrade base`, and do not start the whole Compose project for this: its `init` service runs the upgrade and the seed script.

In `backend/requirements.txt` only FastAPI (0.142.4), Starlette (1.7.0) and Pydantic (2.14.4) are pinned (D82; the middleware guard of D67 (4) is the review point for an upgrade), and the Interview Agent has its own pinned requirements and lock (`interview_agent/`, D79). ## 10. Development rules

1. `pytest` must pass before and after every change.
2. Do not change the architecture, the DB schema, auth, or an existing API contract unless the task asks for it; schema changes always go through a new migration, never edit an applied one.
3. Stay inside the task; small, revertible changes, one purpose each.
4. Before changing a function/endpoint, find its callers (backend and `frontend/src/api/client.ts`).
5. Never commit `.env`, API keys or real CVs; use synthetic data.
6. Every feature must work in `AI_MODE=rules`.
7. Run `alembic` and `uvicorn` from `backend/`, `pytest` from the root.
8. Korean for user-facing text, English for code; AI results include `AI_NOTICE`.

### Keeping this document current

- **Doc first.** When a task adds or changes a table, endpoint, page, env variable or constant, update the affected section of this document as part of that task; decisions go to docs/DECISIONS.md.
- The code is the reference (D87). If the code differs from this document, update the document to match how the project really works and list the differences for Long; if the code's behaviour looks like a bug, report it to Long instead of documenting it as correct.
- Re-check the header commit and the [Known issues](#11-known-issues-and-risks) / [open questions](docs/DECISIONS.md#3-open-questions) lists at each milestone.
- Counts: `pytest --collect-only -q | tail -1`, `/docs`, and the table-list command in §3.
- **Doc-drift guards** (`backend/tests/docs/`, part of every `pytest` run and of CI in `.github/workflows/ci.yml`) compare the docs with the code: links and anchors, D/Q/issue references, the §4.1 table and the tokenless-endpoint sentences vs the routes (including Who), env variables (§9, `.env.example`, Compose), quoted constants and thresholds (§9 and `backend/tests/docs/claims.py`), the demo accounts, the migration range, the §8 tree vs the files, and that the docs are English (no Vietnamese letters; D40). A known, intended difference goes into `backend/tests/docs/allowlist.yaml` with a reason; an entry that is no longer needed fails. A failing guard names the doc place and the code place; the code is the reference (D87), so update the doc unless the code looks like a bug (then report it to Long).
